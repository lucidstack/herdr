title: Work items
description: Review requests, feedback on your pull requests, failing checks, assigned issues, mentions and Jira issues in a sidebar inbox, each one a click away from a ready workspace.
---

Work items bring the things that need you into Herdr before any workspace exists: pull requests waiting for your review, feedback on your own pull requests, failing checks, assigned issues, mentions and Jira issues. They appear in an **inbox** at the top of the sidebar. Pick what to do with one and Herdr prepares the workspace: a Git worktree on the right branch, your editor and Git tools in tabs, and a coding agent briefed with the context.

Nothing runs until you configure a source. Without a `[work_items.github]` or `[work_items.jira]` table, Herdr behaves as if the feature did not exist.

## GitHub

GitHub goes through the [GitHub CLI](https://cli.github.com/), which also handles authentication. Check that it works first:

```bash
gh auth status
```

Then enable the source and map the repositories you have cloned locally:

```toml
[work_items.github]

[[work_items.github.repos]]
name = "acme/app"
path = "~/src/app"
```

### Repositories you have not mapped

Work for a repository that has no `repos` entry can only be handled by the agent without a checkout, such as a review of the downloaded diff. When your clones live in one directory, name it as `clone_root` and Herdr can map such repositories as they come in, for example from your phone:

```toml
[work_items.github]
clone_root = "~/projects"
```

The item then offers **Link or clone acme/api** first. Herdr looks through the directories directly inside `clone_root` for a clone with a remote pointing at the repository, trying the one named after it first, and links it with that remote; worktrees are skipped, so the main checkout is the one linked. When there is none, it clones the repository there with `gh repo clone`, into `~/projects/api`, or `~/projects/acme-api` when `api` is taken. Nothing outside `clone_root` is touched, and a failed clone leaves no directory behind. Once linked, the repository counts as mapped: the choices that need a checkout are available, a review offers **Create worktree**, and the clone is listed under **repositories**.

Linked clones are remembered in `work-items.json` and work exactly like `repos` entries, which win for the same repository. To change one, add a `repos` entry for it.

Every poll runs one GitHub search per event. The defaults:

| Event | Default query | What you can do |
| --- | --- | --- |
| `review_requested` | `is:pr is:open review-requested:@me archived:false` | **Review** it with the agent, in a worktree or from a downloaded diff, and optionally have the agent post its review on GitHub |
| `changes_requested` | `is:pr is:open author:@me review:changes_requested archived:false` | Work on the feedback locally, have the agent address it, then have the agent push and reply |
| `ci_failing` | `is:pr is:open author:@me status:failure archived:false` | Diagnose the failures locally, have the agent fix them, then have the agent push the fix |
| `assigned` | `is:issue is:open assignee:@me archived:false` | Plan it locally, or have the agent implement it |
| `mentioned` | off | Have the agent read the thread and draft a reply |
| `ready_to_merge` | `is:pr is:open author:@me draft:false archived:false`, keeping those approved | Merge it, with any method the repository allows |

Change a query, or switch an event off with an empty string, under `[work_items.github.queries]`:

```toml
[work_items.github.queries]
assigned = ""
mentioned = "is:open mentions:@me"
```

### Pull request state

Every pull request in the inbox shows where it stands on a line of its own, looked up every minute: `gh draft`, `gh awaiting review`, `gh changes requested`, `gh approved`, `gh merged` or `gh closed`, followed by `· CI failing` or `· checks running` while checks fail or run. This includes items marked **✓** that no longer need you but still have a workspace. Without required reviews, GitHub records no review decision, so the latest reviews decide: any reviewer still asking for changes reads as changes requested, and at least one approval otherwise reads as approved. Pull requests shown with the ticket they were opened for use that ticket's line instead.

### Branches

- **Review requests** reviewed in a worktree get a local branch `review/pr-<number>` from the pull request head. A branch you kept from an earlier review is continued on `review/pr-<number>-2`.
- **Your own pull requests** (changes requested, failing checks) use the pull request's head branch. An existing worktree of that branch is reopened, and an existing local branch is reused as it is. Otherwise a new branch tracks the remote one, so `git push` works. Pull requests from forks start from GitHub's copy of the head instead, so pushing needs the fork as a remote.
- **Assigned issues** get a new branch `issue/<number>-<title words>` from the repository's default branch. It does not track anything, so a push cannot land on the default branch by accident.
- **Mentions** and reviews without a worktree download the thread or diff into a scratch directory instead.

### Reviewing a pull request

A review request offers one choice, **Review**. The agent always reviews: it reads the change and reports its findings in its pane. Two switches decide the rest:

| Create worktree | Post to GitHub | What happens |
| --- | --- | --- |
| on | off | A worktree on the pull request head with your tools; the agent reviews it and reports back. It does not change files or commit. |
| on | on | The same, and the agent then shows you its findings and posts them as one review comment. |
| off | off | No checkout: the agent reviews a downloaded diff with `gh` and reports back. |
| off | on | The same, and the agent then posts its review as one comment. |

**Create worktree** is on by default, and only offered for a repository with a local clone, from `[work_items.github] repos` or linked through `clone_root`; without one the agent works from the diff. **Post to GitHub** is off by default, since a comment on GitHub is visible to everyone. The comment is only ever a comment: the agent is told never to approve or request changes. Herdr writes nothing to GitHub itself, so you approve the `gh pr review` command in the agent's own permission prompt. In a worktree, the agent writes the comment to a file outside it, so the worktree stays clean and can be removed. **Review** is highlighted when the dialog opens, even below **Link or clone**, unless no agent is configured for the repository: it is then unavailable, and the item has no default choice.

GitHub items offer no choice that only opens them in the browser. What you do on GitHub reaches Herdr through the pull request's own events, so the item updates anyway. To read the pull request there, use **Open #12 on GitHub** in the item's right-click menu.

### Sending feedback back to reviewers

When the agent addresses review feedback or fixes failing checks, it commits on the branch but never pushes. Once you are happy with the commit, open the item again and choose **Ask agent to push and reply** (or **Ask agent to push the fix** for failing checks). Herdr sends the agent already in the item's workspace a follow-up and focuses it. The agent pushes with a plain `git push` (never a force-push), replies once in each review thread it addressed, and asks the reviewers who requested changes to review again. It does not resolve threads or post other comments. Herdr itself writes nothing to GitHub: every command runs in the agent's pane, so you approve each one in the agent's own permission prompts.

The choice needs a workspace with a running agent. Once every reviewer who requested changes has been asked to review again, by the agent or by you on GitHub, the item reads **Waiting for re-review from @…**. When one of them reviews again while changes are still requested, the item is marked unread and you get a notification. Once nobody requests changes any more, the item leaves the inbox as usual.

### Merging approved pull requests

Your pull requests show up as **ready to merge** once reviews approve them: at least one approval and nobody still asking for changes. This works whether or not the repository requires reviews; GitHub only records a review decision when it does, so Herdr reads the latest reviews themselves.

The dialog lists your default merge method first, then the review follow-ups below, then the repository's other allowed methods, and says who approved it. Merging asks for a second <kbd>Enter</kbd>, since it cannot be undone, and only merges the commit you saw: if someone pushed since, GitHub refuses. When GitHub would refuse anyway (conflicts, a branch behind its base, required checks or reviews), the merge choices are disabled with the reason. The item leaves the inbox once GitHub reports the merge; if the merge fails, the reason shows on the item.

Approvals often come with a nit. The summary counts the reviewers' comments (the approval's own text and inline comments, not your replies), and the dialog also offers the changes-requested choices: work on it locally or ask the agent to address the feedback, both on a worktree of the pull request branch, then ask the agent to push and reply in each thread. It does not re-request review, since the pull request is already approved.

When the pull request is linked to a ticket, the ticket's dialog offers the merge methods and **Ask agent to push and reply** as well; see *Pull requests for your tickets* below.

Worktrees are created through Herdr's own worktree support, so `worktree.created` and `worktree.removed` [plugin hooks](/docs/plugins/) run for them, exactly as for worktrees you create by hand.

### Workflows

Each event has workflow blocks. The first block whose `repos` list includes the repository applies; an empty list applies to every repository:

```toml
[[work_items.github.review_requested]]
repos = ["acme/app"]
on_resolved = "remove"      # remove the worktree once the review is done

[[work_items.github.changes_requested]]
agent = "codex"
tabs = [
  { label = "editor", command = "hx ." },
  { label = "lazygit", command = "lazygit" },
]
```

`agent` is the coding agent started in the first tab; leave it empty to disable the agent-led choices. `agent_args` are passed to it, for example `agent_args = ["--model", "opus", "--effort", "high"]` for Claude Code.

Both default to `work_items.agent` and `work_items.agent_args`, which apply to every workspace Herdr opens from a work item: GitHub and Jira workflows alike, and **Pick next**. Switching every workflow to another agent is one line, and a block that sets its own `agent` or `agent_args` still wins for its repositories:

```toml
[work_items]
agent = "omp"               # default: "claude"
agent_args = []
```

A block's `agent` and `agent_args` override the defaults separately: a block that sets only `agent_args` keeps the default agent, and one that sets only `agent` keeps the default arguments.

`tabs` lists the tabs opened after the agent's tab when the workspace has a checkout, in order. Each tab has a `label` and a `command` typed into it; `{plugin:ID}` in a command is an installed plugin's folder. When a command names a plugin that is not installed, the tab runs its `fallback` instead, or is skipped without one. An empty `tabs` list opens only the agent's tab. By default a worktree gets an **editor** tab (`nvim .`) and a **lazygit** tab.

Review requests default to an **editor** tab and a **review** tab running [herdr-reviewr](https://github.com/persiyanov/herdr-reviewr) with the pull request's base branch fetched and passed as `--base`, so its branch scope shows exactly the pull request's changes; `{base}` in a review-request tab is that base. Without the `persiyanov.reviewr` plugin installed, the review tab falls back to lazygit. See the [configuration reference](/docs/config-reference/) for every key.

reviewr also opens itself as a split beside the agent when a worktree workspace is created. With a review tab in your layout, set `auto_open = false` in `~/.config/herdr/plugins/config/persiyanov.reviewr/config.toml` so it only appears in its tab.

## Jira

Jira Cloud goes through its REST API with an [API token](https://id.atlassian.com/manage-profile/security/api-tokens). Put the token in the environment of the Herdr server (by default `ATLASSIAN_TOKEN`); it is passed to `curl` on standard input, never on the command line. Both classic and scoped tokens work. A scoped token needs `read:jira-user` and `read:jira-work`; add `write:jira-work` to assign and start issues from Herdr.

The server reads the token from its own environment, so changing it in your shell does not reach a running server. To switch to a new token without stopping your panes, run `herdr server live-handoff` from a shell where the new token is set: the replacement server takes the variable named by `token_env` from that shell, and inherits everything else from the old server. A handoff from a server older than this feature keeps the old token; stop and start that server once instead.

```toml
[work_items.jira]
site = "acme.atlassian.net"
email = "you@acme.com"
jql = "assignee = currentUser() AND statusCategory != Done ORDER BY updated DESC"

[[work_items.jira.projects]]
key = "APP"
path = "~/src/app"
branch_template = "{key_lower}-{slug}"   # {key}, {key_lower} and {slug} are replaced
```

The same `[[work_items.jira.issues]]` blocks set the agent and tabs for Jira issues, with `repos` listing project keys. For example, to review the agent's changes in reviewr instead of lazygit:

```toml
[[work_items.jira.issues]]
tabs = [
  { label = "editor", command = "nvim ." },
  { label = "review", command = "{plugin:persiyanov.reviewr}/bin/herdr-reviewr", fallback = "lazygit" },
]
```

Each issue shows its key, its title, and a line with its status and assignee, **unassigned** when nobody has it.

### Pull requests for your tickets

When a ticket's workspace is a worktree of a clone mapped in `[work_items.github] repos`, Herdr looks up the pull request opened from its branch every minute and shows it on a second line, e.g. `gh #11904 · draft` or `gh #11904 · awaiting review · checks running`. This works for Jira issues and for GitHub issues assigned to you. A draft is waiting on you: its line turns amber and the item's dialog offers **Mark pull request ready for review** (the default choice unless the ticket itself needs updating) and **Open pull request**.

A Jira issue keeps its pull request after you close its workspace: while a local branch in the project's clone names the issue (the branch **Continue on…** would reopen), Herdr looks up the pull request opened from that branch instead.

If the same pull request is also in the inbox on its own, for example because it is ready to merge, changes were requested or CI is failing, it shows with the ticket instead: its line turns amber, and the ticket offers what that pull request can do. The dialog leads with the pull request's merge, its default method first, such as **Squash and merge**, then **Ask agent to push and reply**, the other merge methods and **Open pull request**. A merge runs on the pull request exactly as if you had chosen it there, and still asks for a second <kbd>Enter</kbd>. The agent briefs go to the agent in the ticket's own workspace, so **Ask agent to push and reply** waits until the ticket has one. Starting a workspace for the pull request itself stays with its own item: the ticket's right-click menu lists those choices under the pull request's header, with **More pull request choices...** for the rest, and does not repeat the ones the ticket already offers. Status lines start with a service label, `jira` or `gh`; set `ui.sidebar.service_icons = "nerd"` to use Nerd Font icons instead.

While a pull request is open, the ticket no longer offers to start its work: **Ask agent to implement it** is gone, and so is **Continue on…** once the ticket has a workspace. Without a workspace, **Continue on…** stays so that you can reopen the worktree, and its brief tells the agent that the pull request is open and to wait for your instructions, rather than to propose a plan for starting the issue. **Open pull request** is the default unless a choice above it asks for that: a merge, the draft waiting on you or the start reminder's fix. A merged or closed pull request changes none of this. The same goes for GitHub issues assigned to you: once their pull request is open, **Work on it locally** and **Ask agent to implement it** are gone.

Issues of a mapped project can be worked on locally on a new branch from `base_branch`, or from the remote's default branch when unset. When the clone already has a worktree or local branch whose name contains the issue key (from Orca, `git worktree add` or another Herdr), the choice reads **Continue on <branch>** and reopens that work instead of starting a new branch. A worktree that is already open as a workspace in this Herdr is linked as it is, without new tabs or agent. The agent brief carries the description, type, priority, status, labels and comments. Issues of unmapped projects can only be opened in Jira.

### Tickets named in pull request titles

When a pull request's title starts with a Jira issue key, bare or in brackets (`TECH-12 Fix login`, `[TECH-12] Fix login` or `TECH-12: Fix login`), its inbox item shows that issue's status and assignee on a line of its own, e.g. `jira TECH-12 · In Progress · Ada`. Issues already in the inbox are shown as they are there; others are looked up every two minutes. Titles without a key show no such line.

## Using the inbox

- **●** marks a new item, **·** one you have seen, and **✓** one that no longer needs you but still has a workspace. A spinner means Herdr is waiting: for you to finish in the browser, or for a workspace to be prepared.
- **Click** an item to choose what to do. The dialog highlights a sensible default; use the arrow keys and Enter, or click a choice. Once an item has a workspace, clicking the item goes to it. The item stands for its workspace: its agent's status shows at the right end of its first row, and the workspace is not listed again in the spaces list.
- A choice with switches shows them below the list while it is highlighted, such as **Create worktree** and **Post to GitHub** for **Review**, each with a number. Press that number or click the switch to flip it, then press Enter. Clicking a choice that has switches highlights it first, so you can set them; click it again to run it. The right-click menu runs such a choice with its switches at their defaults.
- While a workspace is being prepared, the dialog shows each step: the worktree, then the agent brief. The brief counts as delivered only once the agent starts working. If the agent first asks you something, such as whether to trust the folder, the brief waits for your answer.
- **Right-click** an item for what to do next. The menu leads with the item's likely next steps, its default first, such as **Squash and merge** or **Move APP-7 to Done**, with **More choices...** for the rest; the workspace an item already has is not listed, since a click goes there. Then the item opens in the browser, each link naming where it goes (**Open APP-7 in Jira**, **Open #12 on GitHub**). Then you can **link it to the current workspace** when you already started the work somewhere Herdr did not detect, snooze it for an hour or a day, dismiss it or show it again. Closing the workspace or removing its worktree comes last. Closing a linked workspace unlinks the item again.
- A dismissed item stays hidden until it is requested again. A snoozed item comes back as new when the snooze ends, even across restarts.
- Click the **inbox** header to give the inbox most of the sidebar. The **↓ N more** and **↑ N more** rows page through long lists, and the mouse wheel scrolls one item at a time.
- When the last ticket leaves the inbox, whether done, dismissed or snoozed, its header sparkles **✦ inbox zero ✦** for a few seconds, then settles on **all clear**.
- `prefix+i` opens a keyboard list of every item, hidden ones last: `j`/`k` or the arrow keys select, Enter acts like a click, `m` opens the item's menu, `d` dismisses, `s` snoozes for an hour and `u` shows a hidden item again. Change the key with `keys.inbox`.
- In a collapsed sidebar, a badge shows the number of new items (**●N**), or **!** when a source reports an error. Click it to open the list.
- With several machines connected, the inbox shows the items of the machine in focus.
- A **repositories** group lists each clone mapped in `[work_items.github] repos` and `[work_items.jira] projects`, once per path. Click one to go to the workspace open on its main checkout, or to open one there on whatever is checked out. That workspace sits under its row (collapsed to the agent's status and branch unless focused) rather than in the spaces list, so it stays in reach even with `sections = ["inbox", "agents"]`.

When an item no longer applies (the review is submitted, the checks pass, the issue is closed), it leaves the inbox. If it has a workspace, it stays marked **✓** until you close the workspace, unless its workflow says `on_resolved = "remove"`. Removal never discards uncommitted changes: a dirty worktree is kept and the item says so.

### Keeping the tracker in step

Once an item has a workspace, Herdr checks that its tracker knows you are on it. When a Jira issue is not assigned to you or is still in a to-do status (by status category, whatever your workflow calls it), or a GitHub issue is not assigned to you, the item's key turns amber, and its dialog and the top of its right-click menu say what is missing. One choice fixes it: **Assign to me and move to In Progress**, or just the part that is needed. For Jira it applies the one transition into an in-progress status, or, when the workflow has several (such as a Blocked status in the same category), the one named In Progress; otherwise the choice explains why it is unavailable and **Open in Jira** is still there. The dialog stays open while the change runs: a spinner marks the choice, then the result shows above the choices, **✓** with what changed, or the reason Jira refused it. A refused change can be tried again, for example after replacing a token that lacks `write:jira-work` and running `herdr server live-handoff` from a shell that has the new token. A finished fix is marked **✓** and cannot be repeated. The reminder clears as soon as the tracker catches up, and **Don't remind me for this ticket** silences it for good. There is no notification or sound.

Once the pull request linked to a Jira ticket is merged while the ticket is still open, closing it is what is left to do. **Move APP-7 to Done** leads the item's choices and is the default; the start reminder no longer shows, and **Continue on…** stays below for any follow-up work. It applies the ticket's one transition into a done status, or, when the workflow has several (such as Won't Do), the one named Done. If Jira needs more for that transition, such as a resolution, the choice fails with Jira's reason; close the ticket in Jira instead. Once Jira reports it done, the item resolves as usual.

The agent in the item's workspace hears about what these choices do. Once one succeeds, for example **Mark pull request ready for review** from the phone, Herdr leaves the agent a note saying what changed, so it does not keep working from an out-of-date picture. With the omp or Claude Code integration installed, a working agent gets the note straight away as steering, and an idle one sees it with your next prompt.

### Picking what to work on next

Click **+ Pick next task…** at the bottom of the inbox (or bind `keys.pick_next`, unbound by default) when you are not sure what to take next. Choose the tracker, with Tab or a click when several are configured, and optionally say what you are after. Herdr opens a scratch workspace, **Pick next · Jira** for example, with the agent from `work_items.agent` and briefs it to investigate read-only: `herdr work-item search` and `show`, plus your mapped clones through `git -C`. It recommends one ticket and up to two alternatives, with why now, who works on related tickets and any overlap, then asks you.

Pick next can run another agent, or the same one with other arguments, under `[work_items.pick_next]`; each unset key falls back to `work_items.agent` and `work_items.agent_args`. It starts the agent in plan mode where Herdr knows how: for omp it sends `/plan` before the brief, so the brief is omp's first planning request and omp plans with you before it touches anything. The plan is not approved for you. `plan_command` sets the prompt sent before the brief for other agents, or `""` to send none:

```toml
[work_items.pick_next]
agent = "omp"
agent_args = ["--model", "opus"]
plan_command = "/plan"      # default: "/plan" for omp, nothing otherwise
```

Talk it through in its pane. Once you confirm a pick, the agent adds the ticket to the inbox with `herdr work-item add` and chooses it (the local choice unless you ask for another), so its workspace is set up as usual. It never assigns or transitions the ticket.

Each tracker keeps one discovery workspace. It sits under its own row at the bottom of the inbox rather than in the spaces list, collapsed to the agent's status unless focused. Picking again while it is open focuses it and sends your new context as a follow-up. The dialog remembers the tracker you used last and the last text for each. Once a ticket from that tracker has its workspace, the discovery workspace has done its job and closes, leaving **+ Pick next task…** for next time. It stays open if setting up the ticket's workspace fails.

## Scripts and plugins

Every item change is published as an event: `work_item.created`, `work_item.updated` and `work_item.resolved`, each carrying the item. Plugins can react to them with `[[events]]` hooks, and scripts can subscribe through the [socket API](/docs/socket-api/). Items restored at start-up are not reported as created.

The `herdr work-item` command drives the inbox from scripts and agents:

```bash
herdr work-item list
herdr work-item choose 'github:acme/app#42' review
herdr work-item snooze 'github:acme/app#42' --for 2h
herdr work-item dismiss 'jira:APP-7'
herdr work-item unhide 'jira:APP-7'
herdr work-item link 'jira:APP-7' w3
```

`herdr work-item choose` runs a choice with its options at their defaults. `work_item.list` shows each choice's options as `{ "option_id", "label", "description", "default" }`, and `work_item.choose` takes `options`, the ids to switch on: leave it out for the defaults, or send `[]` to switch every option off. The review choice has the options `worktree` and `post`. An id the choice does not offer fails with `unknown_option`, and nothing runs.

Preparing a workspace is reported as the item's `provisioning`: its `steps`, whether they are `finished` and, once they are, `finished_at`, the Unix time in seconds at which the last one ended.

### What needs you

Herdr works out whether each item needs you, and why, and reports it as the item's `attention`: a `kind` and a one-line `reason`, plus the agent's `pane_id` for agent kinds and `since`, when it entered that kind. Items that do not need you have no `attention`. From most to least urgent:

| Kind | When |
|---|---|
| `blocked` | An agent in the item's workspace waits on you. The reason is the prompt the agent reported, when its integration reports one. |
| `failed` | Setting up the workspace or carrying out a choice failed, or the workspace could not be removed. A failed agent brief stops counting once an agent in the item's workspace has finished a turn after it: the agent worked, so it was ready after all. The step stays failed in `provisioning`. |
| `finished` | An agent in the item's workspace finished its turn and its pane got no input for two minutes since. Typing, pasting or prompting it after the turn ended, or dismissing it with `agent.dismiss`, counts as dealing with it. |
| `changes_requested`, `checks_failing`, `ready_to_merge` | What the tracker asks of your pull request, including the one linked to a ticket. |
| `ready_to_close` | The pull request linked to a Jira ticket is merged, but the ticket is still open. |
| `new` | A review request, assignment, mention or Jira ticket you have not made a choice for yet. |

While an agent in the item's workspace is working, or Herdr is setting up the workspace or carrying out a choice, the tracker's asks wait: someone is already on it. Hidden items, items waiting on others, and items you chose to handle on GitHub or Jira carry no tracker asks. A start reminder is shown on the item but is never a need.

`attention.changed` is published when an item starts or stops needing you, or needs you for another kind of reason, and never again while the kind stays the same. It carries `item_id`, `workspace_id`, a `title` and the new `attention` (absent once it no longer needs you). Needs found at start-up are recorded without events.

Agents in panes outside every item's workspace are covered too, so none goes unnoticed: `herdr work-item list` returns them under `agents`, each with its pane, workspace, status and `attention` (`blocked` or `finished`, by the same rules), and `attention.changed` reports them with a `pane_id` instead of an `item_id`.

`agent.dismiss` counts an agent's finished turn as dealt with, so its `finished` attention clears, for agents inside an item's workspace and outside alike. It takes the agent's pane as `target`. A `blocked` agent has to be answered instead and fails with `agent_blocked`. An agent whose turn does not need you yet, because it is working, ended its turn less than two minutes ago, or was dealt with already, is left as it is.

### Read, search and add tickets on demand

Beyond the sidebar's own queries, `search` and `show` read any ticket through a configured source's credentials, and `add` brings one into the inbox by hand:

```bash
herdr work-item search github 'is:open author:me'
herdr work-item search jira 'project = APP AND text ~ "login bug"'
herdr work-item show github acme/app#42
herdr work-item show jira APP-7
herdr work-item add github acme/app#42
herdr work-item add jira APP-7
```

`search` takes GitHub search syntax for the `github` source and JQL for `jira`, and returns each match's key, title, status, assignee and update time. `show` returns one ticket's full details: description, status, assignee and comments (the pull request or issue body for GitHub).

`add` fetches the ticket and inserts it into the inbox as an ordinary item, so `choose` works on it exactly as if the sidebar's own query had found it. It survives later polls even when the ordinary query does not return it: the item stays in the inbox until the tracker reports the ticket done (checked whenever it is next prepared) or you dismiss it. If a later poll does return it — for example once it is assigned to you — it becomes an ordinary item from then on, indistinguishable from one the sidebar found itself. Adding a key already in the inbox is a no-op; it returns the existing item.
